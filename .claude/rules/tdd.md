# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만" 예외를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 계약, 에러 처리)
- 유틸 함수 (순수 함수, 변환/파싱/정규화)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (스타일, 레이아웃, 마크업만 있는 컴포넌트)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **적용한다.**

## RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.
- 테스트가 처음부터 통과하면 그 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화, 확장 지점을 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 리팩터링 중 테스트를 수시로 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 한 사이클이 끝나기 전에 다음 동작을 구현하지 않는다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두고 보면서 다시 작성하는 것 모두 포함한다.
- 삭제한 코드를 기억에서 되살려 그대로 다시 쓰지 않는다. 테스트가 요구하는 만큼만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 30초면 끝난다. 단순함은 테스트를 생략할 이유가 아니라 **가장 싸게 RED를 볼 수 있는 이유**다. 이후 변경에서 깨지는 곳도 대개 단순한 코드다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 **항상 통과**한다. 실패를 본 적 없는 테스트는 아무것도 검증하지 못한다. 그리고 "나중"은 오지 않는다. |
| "시간이 없다" | 테스트 없이 만든 코드의 디버깅과 회귀 수정이 **더 많은 시간**을 쓴다. 급할수록 짧은 사이클로 가야 한다. |
| "삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 **더 큰 비용**이다. 테스트로 다시 쓰는 것은 보통 훨씬 빠르다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 어차피 삭제 대상이다. **남길 코드라면 TDD로 작성한다.** |
