# Commit

변경사항을 분석해 컨벤션에 맞는 커밋을 만든다. 사용자 승인 없이는 커밋하지 않는다.

## 절차

### 1. 변경사항 분석

아래 명령을 병렬로 실행해 현재 상태를 파악한다.

- `git status` — 변경·추적되지 않는 파일 목록 (`-uall`은 쓰지 않는다)
- `git diff HEAD` — 스테이징 여부와 관계없는 전체 변경 내용
- `git log --oneline -10` — 이 저장소의 기존 메시지 스타일 확인

git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 멈춘다.

다음 파일은 커밋 대상에서 제외하고, 포함되어 있으면 사용자에게 알린다.

- `.env`, 키·토큰·자격 증명이 들어 있는 파일
- `node_modules/`, `dist/` 등 빌드 산출물

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적(예: 기능 추가와 설정 변경)이 섞여 있으면 나눈다.
- 같은 목적에 속한 파일은 함께 묶는다. 구현과 그 테스트는 같은 커밋에 둔다.
- 분류 기준이 모호하면 억지로 쪼개지 말고 하나로 묶은 안을 기본으로 제안한다.

### 3. 커밋 메시지 작성

형식: `타입: 요약`

| 타입 | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능·디자인 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 의존성, 문서, 빌드 등 기타 |

규칙:

- 요약은 한국어로, 명령형이 아닌 간결한 명사형·평서형으로 쓴다. 마침표는 붙이지 않는다. (예: `feat: 다크 테마 토글 추가`)
- 요약은 50자 안팎으로 유지한다.
- 무엇을 했는지보다 왜 했는지가 중요하면 한 줄 비운 뒤 본문에 이유를 적는다.
- 세션 지침이나 CLAUDE.md에 커밋 attribution 문구가 지정되어 있으면 메시지 끝에 그대로 붙인다.

### 4. 사용자 승인 후 커밋

1. 커밋 계획을 보여준다. 커밋마다 메시지와 포함할 파일 목록을 표시한다.
2. 사용자의 승인을 기다린다. 수정 요청이 오면 계획을 고쳐 다시 보여준다.
3. 승인되면 커밋 단위마다 해당 파일만 이름을 지정해 `git add`한 뒤 커밋한다. `git add -A`와 `git add .`은 쓰지 않는다.
4. 메시지는 HEREDOC으로 전달해 줄바꿈과 특수문자가 깨지지 않게 한다.
5. 모두 끝나면 `git log --oneline`으로 결과를 보여준다.

## 금지 사항

- 사용자가 요청하지 않은 `git push`, `--amend`, `--force`, `--no-verify`
- pre-commit hook이 실패했을 때 우회하는 것. 원인을 고치고 새 커밋으로 다시 시도한다.
- 승인받은 계획에 없는 파일을 커밋에 추가하는 것
